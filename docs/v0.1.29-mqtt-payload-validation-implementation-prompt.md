# Implementation prompt: MQTT payload validation and reporting refinement

Status: implementation completed locally in commit `a27d193`; retain this
prompt for review and field follow-up.

Use this prompt to review the v0.1.29 refinement in the Smart Commissioning App.

## Role

You are the senior engineer responsible for the shared Python validation core, FastAPI service, report renderers, and React operator console. Work in the existing repository and preserve all unrelated local changes.

## Objective

Implement and review ten connected changes:

1. Size automatic shared MQTT capture for the concrete validation-topic count.
2. Find a registered asset that publishes under a wrong MQTT path within a safe project or site namespace.
3. Count and list unique registered assets seen on wrong topics.
4. Produce an annotated copy of the exact input register used by the run.
5. Show absent metadata and pointset payloads as `Not received` without per-point issue fan-out.
6. Add an accessible jump from a long issue list to the same payload's expected-vs-observed control.
7. Let an engineer delete one or several generated reports without deleting source runs or shared synchronized evidence.
8. Generate PDF, DOCX, XLSX, and ZIP from one frozen title and scope.
9. Give the expanded asset group one continuous tonal outline.
10. Prepare the release note and field acceptance checklist without claiming field acceptance.

The concrete failure to remove is an absent pointset turning into dozens of amber issue cards. The operator needs one honest absence state and a direct route to the payload comparison.

- Preserve every existing user change in the dirty working tree.
- Use `apply_patch` for hand edits.

## Required behavior

### Automatic capture capacity

- Preserve an explicitly supplied positive `max_messages` value.
- When no positive value is supplied, use the larger of 500 or the number of
  concrete validation filters.
- Apply the same effective capacity to the retained expected-topic capture and
  its secondary bounded measurement.

### Wrong-topic identity and routing

- Build the current concrete expected subscriptions first.
- Derive one bounded observation scope from their literal roots.
- Widen by at most one safe parent level when the strict common parent would hide a neighbouring wrong path.
- Never subscribe to a bare `#` solely for this feature.
- Match asset identity as an exact, case-sensitive MQTT topic segment.
- Route only when one unique, non-ambiguous register asset matches.
- Map state, metadata, and pointset suffixes to that asset and retain the actual topic.
- Validate the payload content even when the topic is wrong.
- Add a deterministic topic-mismatch finding with expected and actual topic values.
- Keep expected-topic completion semantics unchanged.
- Remove mapped registered assets from the unrelated `unexpected_devices` inventory.
- Leave unregistered and ambiguous publishers as supporting unexpected evidence.

### State and metrics

Model these separately:

- Observation: observed, not received, or not observed after a live capture window.
- Topic: expected, wrong, or not evaluated.
- Payload: pass, pass with notes, or non-compliant.

Add an optional wrong-topic asset collection and unique count to `validation_summary_v1`. Include asset ID, system, expected root, actual root, payload type, expected topic, actual topic, and last seen where evidence exists.

### Missing payloads

- When the `pointset_payload` key is absent, skip point-level missing, unexpected, and probable-misname comparisons.
- When the key exists with `{}`, treat the payload as observed and validate it.
- In the verdict helper, an unobserved payload returns neutral `Not received` before issue-severity branches, except for the established asset-level `Not observed this run` state from a real live capture window.
- Keep the expected-vs-observed control available for an absent expected payload.

### Annotated register

- Bind the exact import ID and original filename when validation starts.
- Freeze original accepted rows, column order, values, and row order into safe run evidence.
- Never query a later latest import while generating or downloading a report.
- Add `Wrong Topic Assets` and `Annotated Input Register` XLSX sheets.
- Add `wrong_topic_assets.json` and `annotated_input_register.json` ZIP members.
- Keep the source `Expected topic` column in place. Append: `Observed in run`, `Topic status`, `Actual topic(s)`, `Comment`, `Source run ID`, and `Observed at`.
- Use `Not evaluated` for the topic status of an unobserved row.
- Add a compact wrong-topic section to DOCX and PDF reports.
- Count unique registered assets, while detail rows may include several payload types and topics.

### Long issue lists

- At eight or more issue cards, show `Jump to payload comparison` near the payload heading or verdict.
- Keep a ref map keyed by asset ID and payload type.
- Scroll to the same payload's comparison control and move focus to it.
- Use smooth scroll unless `prefers-reduced-motion: reduce` is active, then use automatic scroll.
- The control must be keyboard operable and must not hide any issue or payload content.

### Report deletion

- Add `POST /reports/delete` with JSON `{ "report_ids": [...] }`.
- Require at least one ID and engineer permission.
- De-duplicate IDs while preserving request order.
- Resolve and validate the whole batch before mutation.
- Return 404 for an unknown ID or a run whose job type is not `report_generation`.
- Delete validated report rows in one transaction and rely on existing foreign-key cascades.
- Return deleted IDs, count, and local artifact cleanup warnings.
- Delete only a path-safe report-owned local artifact after the transaction.
- Treat a missing file as already clean.
- Preserve content-addressed sync files under `sha256/`.
- In React, add row deletion and selected deletion. Confirm with report name or count, invalidate the reports query, clear deleted selections, and show success or failure.
- Keep export restricted to succeeded reports. Allow deletion selection for any generated report.
- Hide or disable deletion for viewers and explain the permission requirement.

### Release documentation

- Use the v0.1.21 release-body structure for local release notes: one release
  heading, a factual introduction, `What changed`, and
  `Windows portable download`.
- Keep the publisher tokens `{{COMMIT}}`, `{{EXE_SHA256}}`, and
  `{{ZIP_SHA256}}`.
- Normalize any later release note that drifted from that structure without
  changing its historical facts.
- Create `docs/release-notes-v0.1.29.md`.
- Create `docs/v0.1.29-field-acceptance-checklist.md` for the unfiltered
  554-asset two-hour run and the longer cadence run.
- State plainly that v0.1.29 has not passed field acceptance until both runs
  pass.
