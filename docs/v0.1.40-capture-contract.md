# v0.1.40 MQTT capture contract

## Termination truth table

| Transport termination | `window_completed` | External termination reason | Run consequence |
| --- | --- | --- | --- |
| finite monotonic deadline elapsed | true | `window_elapsed` | eligible to succeed |
| cancellation observed | false | `cancelled` | cancelled |
| broker interruption | false | `broker_interruption` | failed/incomplete |
| primary topic or byte cap | false | `message_cap` or `byte_cap` | failed/incomplete |
| finite list-only legacy adapter | false | `capture_outcome_unavailable` | failed/incomplete |
| indefinite expected topics complete | false | `required_topics_received` | normal indefinite completion |
| indefinite backstop | false | `backstop_elapsed` | failed/incomplete |

Finite validation deliberately ignores expected-topic completeness. A capture
window is a measurement interval, so only the transport's monotonic deadline
evidence can yield `window_elapsed`.

## Retention ownership and limits

The transport owns retained MQTT evidence. Its primary lane holds the latest
payload for each expected concrete validation topic. New primary topics are
bounded by the validation topic capacity and a configurable byte admission
limit (256 MiB by default). This holds roughly 112 KiB for each of the 2,340
payload families in the 780-row field contract. A replacement remains current
only when its projected lane total stays within that bound; an oversize primary
replacement keeps the prior evidence and ends incomplete with `primary_byte_cap`.

The secondary lane is diagnostic-only. It defaults to 2 MiB and an independent
topic count. New or replacement diagnostic topics beyond either bound retain
their previous evidence, record which secondary limit truncated them, and do
not end a finite validation window. Raw
evidence remains separately redacted and bounded by the existing validation
evidence policy.

## Compatibility

`subscribe_and_capture` still returns `list[MqttMessage]` for existing callers.
Production UDMI validation calls `subscribe_and_capture_with_outcome`, whose
typed outcome carries messages, termination, deadline evidence, cancellation,
primary-cap state, secondary truncation, and byte/count telemetry. A legacy
injected adapter may still return a list, but a finite run then has no evidence
of deadline completion and is reported incomplete instead of inferred as a
success.

## Register applicability

Effective payload applicability and its source are persisted independently:

1. valid nonblank `Payload applicability`: `explicit_applicability`;
2. otherwise valid nonblank `Payload type`: `explicit_payload_type`;
3. both blank: state, metadata, pointset with `legacy_blank_default`;
4. invalid explicit values remain invalid and have no effective types.

Gateway/DDC rows may leave Expected points and Expected units jointly blank.
Units without points remain an import error.
