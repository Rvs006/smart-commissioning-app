# v0.1.42 protocol-recovery validation

Status: field-validation guide for the v0.1.42 release. It does not attest that
live field lanes have passed.

This record covers the repairs merged through pull request #138 on 2026-08-13.
The merge commit is `ad63a784d83aeafa4e52fce9b842865ed7047245`. An earlier
local portable candidate was preparatory test evidence only. The official
release asset must be built from the signed v0.1.42 tag and verified by its
matching Windows workflow evidence.

## What changed

- A blank IP target editor now explicitly asks the backend to use accepted
  addresses from the imported IP register. Exclusions can still narrow that
  register-driven scan.
- BACnet Preview now follows the sealed-preview flow. A live BACnet run uses
  the matching one-use authorization instead of treating Preview as a live
  submission.
- The configured BACnet UDP port reaches the discovery transport. Persisted
  BACnet point values, identifiers, units, and attributes now map into the
  **Points / Live Data** table.
- MQTT terminal Results rely on the sealed run and result snapshot. A failed
  supplementary topic refresh cannot hide those results.
- The portable build removes copied virtual environments and stamps the
  requested version into health and report evidence.

## Field validation sequence

Run each lane on approved equipment during the agreed change window. Start with
a preview every time and retain the run identifiers privately.

### IP

1. Import the approved IP register.
2. Leave the target editor blank when the accepted register is the intended
   target source. Add only the exclusions that are genuinely needed.
3. Preview the run and confirm the source interface, addresses, ports, and
   exclusions.
4. Create or select the authorization tied to that preview, then run live.
5. Confirm the result identifies the register-derived targets and does not
   return an empty-target validation error.

### BACnet/IP

1. Save the actual BACnet UDP port, source interface, instance range, and
   BBMD or foreign-device settings when the site uses them.
2. Preview the plan. Confirm its port and interface before authorizing a live
   run from that exact preview.
3. Run live on a lab segment first, then the approved site segment.
4. Confirm discovered devices and open **Points / Live Data**. Record a sample
   device instance, point name, observed value, and unit from the persisted
   table.

### MQTT

1. Set the broker, TLS and authentication material, topic filter, and finite
   capture window. Keep credentials out of any exported evidence.
2. Preview the capture, then authorize and run it on the approved broker.
3. After terminal completion, open **Results** and confirm the sealed rows are
   available. If the live-topic panel reports a temporary refresh problem,
   capture that diagnostic but keep the terminal result evidence.

## What this candidate does not prove

The completed checks do not prove real BACnet controller interoperability, a
live broker capture, an on-site IP sweep, or a Docker image build. Those need
the field evidence described in [the on-site validation checklist](phase5-onsite-validation.md)
and [the protocol conformance record](protocol-conformance.md).

Record the approved register revision, source interface, preview and live run
IDs, released EXE hash, packet or broker evidence, and operator sign-off in the
private field store.
