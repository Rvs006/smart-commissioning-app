# MQTT payload validation and reporting refinement

## Outcome

This change will let a commissioning engineer find a registered asset even when it publishes below the wrong MQTT path, show that distinction in the UI and report, return an annotated copy of the input register, remove the missing-point card explosion when no pointset arrived, jump past long issue lists, generate all four report formats together, distinguish the expanded asset group, and delete one or several generated reports.

A wrong-topic device should never be collapsed into "not observed". That is the most dangerous lie in this workflow because the engineer can see traffic on the broker while the tool claims silence.

The supplied v0.1.27 field export establishes the gap: 554 imported assets,
287 observed, and 267 not observed, with no retained wrong-topic asset list or
frozen register snapshot. Those 267 rows cannot be classified safely from the
old report. v0.1.29 must create the missing evidence during a fresh run.

## Product decisions

These decisions resolve the unclear parts of the notes without blocking implementation:

1. The current repository is already at v0.1.28, so this work is tracked as the next v0.1.29 refinement.
2. A wrong-topic payload counts as observed. Its content is still validated.
3. Asset identity is matched against a complete, case-sensitive MQTT topic segment. Substring matches are rejected.
4. An identity match must resolve to exactly one register asset. Ambiguous IDs remain unassigned evidence.
5. Search stays inside a bounded common project or site namespace and never subscribes to a bare `#` solely for wrong-topic detection.
6. An absent payload produces no derived per-point findings. A present but empty `{}` payload remains observed and is validated.
7. The UI label remains `Pointset - Not received`, matching the product vocabulary rather than the document's generic `Payload` label.
8. The jump action appears when a payload has eight or more issue cards.
9. The annotated register keeps original columns and row order, then appends observation and topic-review columns.
10. Wrong-topic totals count unique registered assets. Detail rows retain payload type, expected topic, and actual topic.
11. Report deletion requires engineer permission, explicit confirmation, and removes the generated report database record plus its report-owned local file. Source runs remain untouched.
12. Shared content-addressed sync files are retained because several records may reference the same bytes. Their database references can cascade with the report row.
13. The current observed and not-observed filters remain unchanged. Topic matching belongs in capture and classification, not in another UI filter.
14. An explicit `max_messages` remains an operator ceiling. With no explicit value, shared capture uses the larger of 500 or the number of concrete validation filters.
15. Generate All creates PDF, Word, Excel, and evidence-pack reports from one frozen run scope and title. A partial failure identifies the formats that did not complete.
16. The active asset drill-down uses one continuous, non-glowing outline around its header and payload content.

## State model

Observation, topic compliance, and payload compliance are separate facts.

| Observed | Topic status | Payload status | Display |
| --- | --- | --- | --- |
| No | Not evaluated | Not evaluated | Neutral: `Not received` |
| No, after a live capture window | Not evaluated | Not evaluated | Red: `Not observed this run` |
| Yes | Expected topic | Compliant | Green: `Pass` |
| Yes | Expected topic | Non-compliant | Amber: `Non-compliant` |
| Yes | Wrong topic | Compliant | Observed, wrong topic, payload passes |
| Yes | Wrong topic | Non-compliant | Observed, wrong topic, payload has issues |

Selection styling remains a table interaction state. It does not become a fourth validation colour.

## Workstream 1: bounded wrong-topic discovery

### Capture algorithm

1. Build the existing concrete state, metadata, and pointset subscriptions for every accepted register asset.
2. Derive one literal expected publisher root for each asset.
3. Compute a bounded observation scope from the common parent. If every expected root shares a site or floor segment that would hide a neighbouring wrong path, step up one safe parent. Abort this extra measurement when the result would be empty or a bare `#`.
4. For each received message outside all expected roots, split the topic into MQTT levels.
5. Find register asset IDs that equal a complete topic level with case preserved.
6. Route the message only when exactly one unique asset matches and that register identity itself is unambiguous.
7. Map the payload suffix to state, metadata, or pointset. Keep the actual topic on the observation.
8. Add one deterministic topic-mismatch finding per affected payload type. Record expected and actual topics and a clear corrective action.
9. Exclude these mapped publishers from `unexpected_devices`. Unregistered and ambiguous publishers remain in that supporting list.
10. Keep expected-topic completion rules unchanged. A wrong-topic message can be validated, but it does not prove that the configured expected subscription published.

## Workstream 2: honest missing-payload handling

The point comparison currently treats an absent pointset as an empty observed point map, then creates one high-severity issue for every expected point. The correction is keyed to payload presence:

- `pointset_payload` absent: skip missing, extra, and probable-misname comparison.
- `pointset_payload` present as `{}`: run structural and point comparison because the broker delivered a payload.
- Missing metadata or pointset: show `Not received`, keep the expected-vs-observed control, and show no invented point cards.
- Received malformed payload: retain its real findings and amber status.

The frontend verdict helper also gives direct observation priority over issue counts. This protects old retained runs that contain synthetic missing-point findings.

## Workstream 3: annotated input register

The validation run will freeze the exact import ID, original filename, accepted row order, original columns, and accepted row values in safe run evidence. A report must never query whichever register happens to be newest at download time.

The XLSX output gains `Wrong Topic Assets` and `Annotated Input Register`
sheets. The ZIP output gains `wrong_topic_assets.json` and
`annotated_input_register.json`. DOCX and PDF gain a compact wrong-topic detail
section; a complete register table belongs in XLSX because wide source
registers do not read well on A4 pages.

Appended columns:

The register's existing `Expected topic` column stays in its original position and is not duplicated.

| Column | Values |
| --- | --- |
| Observed in run | Yes / No |
| Topic status | Expected topic / Wrong topic / Not evaluated |
| Actual topic(s) | Deduplicated captured topics |
| Comment | Plain-language review result |
| Source run ID | Run that supplied the evidence |
| Observed at | Latest retained observation time |

For an unobserved row, topic status is `Not evaluated`. Writing `No` under `Correct topic?` would claim that a topic was inspected when no message existed.

## Workstream 4: report deletion

### API

`POST /api/v1/reports/delete`

Request:

```json
{
  "report_ids": ["report-1", "report-2"]
}
```

Response:

```json
{
  "deleted_report_ids": ["report-1", "report-2"],
  "deleted_count": 2,
  "artifact_cleanup_warnings": []
}
```

Rules:

- Engineer role or higher.
- One to many IDs, order-preserving de-duplication.
- Validate every ID as `report_generation` before deleting anything.
- Return 404 for an unknown or non-report ID and leave the full batch unchanged.
- Delete report rows in one database transaction.
- Rely on existing foreign-key cascades for issues, result, seal, dispatch, context, conflicts, and sync-reference rows.
- Remove only report-owned local artifact paths after the database transaction.
- Ignore a missing local file as an idempotent cleanup case.
- Reject path traversal and preserve `sha256/` content-addressed files.

### UI

- Keep the existing row checkboxes.
- `Export selected` operates on succeeded reports only.
- `Delete selected` operates on any selected generated report.
- Add a row `Delete` action for a single report.
- Show the file name or report title and count in the confirmation.
- Refresh the report list, clear deleted selections, and show a status or error panel.
- Hide or disable destructive controls for viewers with an engineer-permission explanation.
