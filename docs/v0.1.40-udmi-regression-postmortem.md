# v0.1.40 UDMI early-success regression postmortem

## Root cause

The v0.1.39 register path treated blank Payload type/applicability as an
unresolved matrix. That created no effective validation topics for a field
register whose 780 rows deliberately left both columns blank. Broad traffic
then occupied the shared 500-topic retention cap in about 400 seconds. The
validation layer saw the returned list, inferred a time-window completion, and
labelled the run `window_elapsed` and `SUCCEEDED` even though the requested
two- or ten-hour window had not elapsed. Thousands of deliveries and roughly
263-282 registered asset IDs were visible, while expected/received reporting
could collapse to 0/0.

## Why v0.1.39 did not fix it

v0.1.39 separated some primary and secondary retention, but it preserved the
unresolved-blank applicability decision and list-only completion inference.
It therefore had no authoritative transport termination signal and could still
mistake a capacity exit for elapsed time.

## Correction and test gap

v0.1.40 restores the proven blank-register contract through an explicit
`legacy_blank_default` provenance source, producing three effective families
per asset. It makes the transport outcome authoritative, prevents finite
expected-topic early stop, and treats diagnostic saturation as non-terminal
telemetry. Latest expected validation evidence has a bounded 256 MiB primary
budget, sized for the 780-row contract; diagnostic evidence retains its small,
independent 2 MiB budget. The regression suite crosses importer, schedule expansion, and
transport outcome handling with a 780-row register, 2,340 expected payloads,
and more than 500 diagnostic topics. The missing boundary test was the gap:
earlier tests independently checked import and capture behavior, but did not
prove that the imported blank rows reached the live transport with truthful
termination evidence.
